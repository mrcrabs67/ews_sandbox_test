# Solution

## State placement

- **URL state** — текущая заявка (`/tickets/:ticketId`) определяется через `matchPath` в `WorkspaceShell`. Никакого дублирующего глобального `currentTicketId` не создано.  
  *Почему*: URL является источником истины для текущего маршрута, и все зависимые компоненты (палитра, детальная страница) получают `ticketId` из роутера или через проброс пропсов/колбэков.

- **Browser state** — недавно открытые заявки хранятся в `localStorage` под ключом `ticket-workspace:recent-ticket-ids`. Логика чтения/записи изолирована в модуле `recentTicketStorage`.  
  *Почему*: localStorage позволяет сохранять историю между сессиями без участия серверного API. Чистый модуль без привязки к React упрощает тестирование.

- **API/cache state** — все заявки загружаются через RTK Query (`useGetTicketsQuery`, `useGetTicketQuery`). Мутации (`markTicketInProgress`, `markTicketReviewed`) инвалидируют теги, автоматически обновляя кэш.  
  *Почему*: RTK Query обеспечивает централизованное кэширование и согласованность данных без ручного управления запросами.

- **UI state** — черновики оператора на странице заявки хранятся локально в `TicketDetailPage` (useState).  
  *Почему*: это временное состояние, относящееся только к одному компоненту; его не нужно поднимать в глобальный стор.

## Boundaries

Граница между command palette и ticket feature проходит по контракту `CommandDefinition`.
- **Command palette** (`app/command-palette`) остаётся универсальным рантаймом: он не импортирует ни типы заявок, ни API-хуки.
- **Ticket-aware команды** собираются в `workspaceCommands.ts` на основе параметров, переданных из `WorkspaceShell`. Колбэки `onOpenTicketList` и `onMarkTicketReviewed` замыкаются на хуки (`useNavigate`, `useMarkTicketReviewedMutation`) в оболочке.
- Сам `WorkspaceShell` получает текущий тикет через разбор URL (`matchPath`), а не из глобального состояния.

Таким образом, бизнес-логика заявок не протекает в generic-слой командной палитры.

## Edge cases covered

- **localStorage недоступен/выбросил исключение** → `readRecentTicketIds` возвращает `[]`.
- **Повреждённый JSON / не-массив** → после парсинга проверяется тип; при несоответствии возвращается `[]`.
- **В массиве id присутствуют пустые строки или нестроковые элементы** → фильтруются внутри `readRecentTicketIds` (type predicate, проверка длины).
- **ID из хранилища больше нет в текущем API-ответе** → при формировании `recentTickets` в `TicketListPage` id, не найденные в массиве `tickets`, отбрасываются.
- **Список недавних заявок пуст** → показывается сообщение "No recently opened tickets yet."
- **Повторное открытие той же заявки** → поднимает её наверх, дубли исключаются.
- **Команды палитры вне страницы заявки** → проверка `if (currentTicket)` гарантирует, что ticket-специфичные команды не появляются на списке заявок.
- **Быстрое повторное открытие палитры** → фокус восстанавливается на ранее активном элементе, состояние сбрасывается.

## Trade-offs

- Команда "Mark as reviewed" доступна и для уже проверенных заявок. Мутация идемпотентна, поэтому повторное выполнение не ломает UI, но мы избежали усложнения логики (disabled на основе текущего статуса).
- В `readRecentTicketIds` фильтруются только пустые строки и не-строки, но не проверяется формат ID. При изменении формата id (например, префикс) фильтр останется безопасным, но могут появиться невалидные id — их отсеет UI при сверке с API-ответом.
- `recentTickets` вычисляется при каждом рендере через `useMemo` с зависимостью от `tickets`. Дополнительная мемоизация не требуется, т.к. список невелик.
- В тестах команды палитры используется реальный RTK Query и маршрутизатор, что делает тест интеграционным, но несколько медленнее unit-теста. Это оправдано проверкой полного пользовательского сценария.
- Для теста списка недавних заявок замокан `readRecentTicketIds`, чтобы избежать зависимости от реального localStorage и обеспечить стабильность.
